# Scanner confidence calibration

> The "honesty brand" moat, made concrete. A displayed confidence number is a
> promise; this document is how we keep it honest.

## The problem

GPT-4o Vision reports a raw self-confidence (0–100) per candidate strain. That
number is badly miscalibrated. On the baseline eval (`data/eval/baseline-textonly-2026-06-23.json`,
n=50 curated reference photos), the model reports ~60 on average whether it is
right or wrong, and dumps ~90% of scans into a 50–79 "moderate" band whose
**actual top-1 accuracy is ~10%.**

Reliability of the **raw** model confidence (baseline eval):

| Raw stated confidence | count | actual top-1 correct |
|---|---|---|
| 50–59 | 8 | 13% |
| 60–69 | 32 | 6% |
| 70–79 | 4 | 0% |
| 80–89 | 2 | 100% |

Correct answers averaged **68** stated confidence; wrong ones averaged **59** —
barely separable. A user reading "65% confident" is being misled.

## The approach — evidence-anchored + structured signals

We do **not** pretend a precise isotonic/Platt fit: n=50 with ~5 correct is far
too thin, and a false-precision curve would itself betray the honesty brand.
Instead:

1. **Two strata**, split by the strongest real discriminator in the data —
   whether OCR read a strain name off the image (`matchSignals.nameInImage`):
   - **`visualOnly`** — bare flower, no readable label. **Fit from evidence:**
     per raw-confidence bin, empirical P(correct) is Bayesian-shrunk toward the
     dataset's own base rate (strength K=5, so a 2/2 bin does **not** become
     "100%"), then PAVA-pooled to be monotone non-decreasing in raw.
   - **`nameInImage`** — OCR read a plausible strain name. This is the genuinely
     reliable lane (the 80+ / 100%-correct cases are OCR cases). We have **no eval
     labels for it yet**, so it is a **declared conservative prior**
     (`source: "prior"`), not a fit. Marked as such; replaced once the flywheel
     (`scan_corrections`) yields labeled OCR cases.

2. The calibration table is a **versioned, auditable JSON**
   (`data/scanner/calibration.json`), regenerated by
   `npm run scanner:calibrate` — not hard-coded magic numbers.

### Current fitted table (visualOnly)

| Raw | n | empirical top-1 | **calibrated** |
|---|---|---|---|
| 0–39 | 2 | 0% | 7% |
| 40–49 | 2 | 0% | 7% |
| 50–59 | 8 | 13% | 8% |
| 60–69 | 32 | 6% | 8% |
| 70–79 | 4 | 0% | 8% |
| 80–100 | 2 | 100% | 36% |

The whole 0–79 visual range collapses to its true ~7–8%; even the model's "80+"
shrinks to a conservative 36% (from a 2/2 sample) instead of claiming certainty.

`nameInImage` prior: raw <60 → 55, 60–79 → 70, 80–100 → 85.

Tiers (from calibrated value): `high` ≥ 70, `moderate` ≥ 40, `low` ≥ 20, else
`uncertain`.

## How it's wired

- `lib/scanner/calibration.ts` — `calibrateConfidence(raw, { nameInImage })`,
  pure/deterministic, reads the bundled table (with a conservative built-in
  fallback if the file is malformed).
- `app/api/scan/route.ts` → `applyConfidenceCalibration(result)` — a
  **presentation transform** applied only when `SCANNER_CALIBRATION=1`. It
  rewrites each candidate's `confidence` to the calibrated value, preserves the
  model's number as `modelConfidence`, re-orders candidates by the honest number
  (an OCR match can outrank a higher-raw visual guess), and recomputes the
  summary tier / primary pick. The response carries `calibrated: true`.
- Deliberately kept **out of `normalizeAnalysis`** so the eval harnesses keep
  measuring raw model behavior.

## Rollout

`SCANNER_CALIBRATION` defaults **off** (today's raw behavior). Turn on with
`SCANNER_CALIBRATION=1` (same pattern as `SCANNER_FREE_NAMING`), verify, then
make default — matching how free-naming shipped.

## Re-fitting

```
npm run scanner:calibrate                 # fits from the baseline snapshot
node scripts/fit-confidence-calibration.mjs data/eval/<newer-snapshot>.json
```

Re-run whenever a new labeled eval snapshot lands or the flywheel accrues enough
`scan_corrections` to fit the `nameInImage` stratum from evidence instead of a
prior. Commit the regenerated `data/scanner/calibration.json`.

## Known limitations / next

- Tiny sample (n=50, ~5 correct) → the fit is conservative by design, not sharp.
- `nameInImage` is a prior, not yet evidence-backed.
- No finer signal-conditioning (e.g. `categoryMatches`, multi-image agreement)
  yet — the data can't support that granularity today.
- Related roadmap cleanup (separate pass): remove the leftover fabricated
  `confidenceRange` / `indicaPct`-`sativaPct`=50 / `consensusStrength` fields
  from the live scanner UI (they come from the disconnected hybrid pipeline).
